# MCP-сервери проєкту (Task A)

**Хост(и), у якому налаштовано:** Claude Code (config-рівень; див. застереження
про верифікацію нижче)
**Файл конфігурації:** [`.mcp.json`](../../.mcp.json) у корені репо

> ## ⚠️ Що саме перевірено, а що ні — читайте перш за все
>
> Цей прогін виконувався в **неінтерактивному агентському середовищі без
> можливості під'єднати MCP-хост**. Тому я розділяю твердження на два класи:
>
> | | Статус |
> |---|---|
> | Пакети існують у npm і реально стартують | ✅ **виміряно** — `npx` + JSON-RPC handshake зі stdin/stdout |
> | Список tools кожного сервера | ✅ **виміряно** — відповідь на `tools/list` |
> | filesystem справді звужує доступ переданим аргументом | ✅ **виміряно** — сервер надрукував свій allowed-list у stderr |
> | Власний сервер відповідає по stdio | ✅ **виміряно** — див. Сервер 3 |
> | Tools з'явилися **у списку інструментів Claude Code** | ❌ **НЕ перевірено** — хост не під'єднувався |
> | `${CLAUDE_PROJECT_DIR:-.}` реально розкривається цим хостом | ❌ **НЕ перевірено** емпірично; підтверджено лише [документацією Claude Code](https://code.claude.com/docs/en/mcp) |
>
> Я **не** стверджую, що бачив ці сервери в UI хоста, бо не бачив.

## Сервер 1 — filesystem

| | |
|---|---|
| **Навіщо** | Дати агенту прямий доступ до `catalog.json` — потрібно для прогону B у Task D (агент має мати шанс відповісти без мого сервера) |
| **Транспорт** | stdio |
| **Як запускається** | `npx -y @modelcontextprotocol/server-filesystem@2026.7.10 ${CLAUDE_PROJECT_DIR:-.}/app/data` |
| **Область доступу (scope)** | **Тільки `app/data/`** — не домашня тека, не корінь репо. Це єдиний каталог, який реально потрібен: там лежить `catalog.json`. Решта репо (в т.ч. `.env`, `.git/`) серверу не видна |
| **Секрети** | Немає — сервер не потребує токена |
| **Версія** | Зафіксована `@2026.7.10`, не `@latest` — щоб мовчазне оновлення пакета не змінило набір tools |

**Які tools він дав агенту** — 14, виміряно через `tools/list`
(`readOnlyHint` узято з відповіді сервера, не з моїх припущень):

| Tool | read-only? |
|---|---|
| `read_file` (deprecated), `read_text_file`, `read_media_file`, `read_multiple_files` | ✅ так |
| `list_directory`, `list_directory_with_sizes`, `directory_tree`, `search_files`, `get_file_info`, `list_allowed_directories` | ✅ так |
| **`write_file`, `edit_file`, `create_directory`, `move_file`** | ❌ **ні — пишуть на диск** |

Тобто 4 із 14 tools цього сервера змінюють файли. Це не «сервер для читання
файлів», як звучить назва, і саме тому область доступу звужена до `app/data`.

**Перевірка, що працює:** запустив сервер напряму і провів handshake
(`initialize` → `notifications/initialized` → `tools/list`). Сервер відповів
`serverInfo: {"name":"secure-filesystem-server","version":"0.2.0"}` і надрукував
у stderr:

```
Client does not support MCP Roots, using allowed directories set from server args: [
  '...\ws6-hw-demo'
]
```

> ### 🔴 Важлива знахідка про scope цього сервера
>
> Той рядок stderr — не косметика. Filesystem-сервер бере область доступу з
> **`roots/list` клієнта**, і лише якщо клієнт не підтримує roots, відкочується
> до аргументів командного рядка. Claude Code roots **підтримує** і відповідає
> на них каталогом запуску сесії плюс усіма `--add-dir`.
>
> Отже: у Claude Code мій вузький аргумент `app/data` — це **fallback, а не
> гарантія**. Реальна область доступу дорівнюватиме робочим каталогам сесії,
> тобто всьому репо. Я лишаю аргумент (він захищає в хостах без roots і фіксує
> намір), але **не вдаю, що він обмежує Claude Code**. Наслідок для загроз —
> у [SECURITY.md](SECURITY.md), розділ 4.

## Сервер 2 — memory

| | |
|---|---|
| **Навіщо** | Зберігати між сесіями факти про домен каталогу (напр. «SKU у форматі XX-9999», «дані синтетичні»), щоб не пояснювати щоразу |
| **Транспорт** | stdio |
| **Як запускається** | `npx -y @modelcontextprotocol/server-memory@2026.7.4` |
| **Область доступу (scope)** | Один JSON-файл knowledge graph. Явно спрямований у `MEMORY_FILE_PATH=${CLAUDE_PROJECT_DIR:-.}/.mcp-memory.json`, щоб він не писав у теку встановлення пакета під `npx`-кешем. Файл додано в `.gitignore` |
| **Секрети** | Немає |
| **Версія** | Зафіксована `@2026.7.4` |

**Які tools він дав агенту** — 9, виміряно: `create_entities`,
`create_relations`, `add_observations`, `delete_entities`,
`delete_observations`, `delete_relations` (усі `readOnlyHint: false`),
`read_graph`, `search_nodes`, `open_nodes` (`readOnlyHint: true`).
Також віддає resource `memory://knowledge-graph`.

**Перевірка, що працює:** handshake пройшов, `serverInfo:
{"name":"memory-server","version":"0.6.3"}`, `tools/list` повернув наведений
перелік.

**Чому цей сервер — свідомий компроміс:** він **не read-only**. Серед його
tools є `delete_entities` / `delete_relations` (`readOnlyHint: false`). Я беру
його усвідомлено, бо він пише виключно у власний gitignored файл і не має
доступу ні до коду, ні до мережі. Розбір — у SECURITY.md.

## Сервер 3 — catalog (власний, Task B)

| | |
|---|---|
| **Навіщо** | Дати агенту авторитетні відповіді «що дозамовити» і «яка вартість запасів» без того, щоб він сам агрегував JSON |
| **Транспорт** | stdio |
| **Як запускається** | `node ${CLAUDE_PROJECT_DIR:-.}/mcp-server/dist/server.js` (потрібен попередній `cd app && npm run build`, потім `cd mcp-server && npm install && npm run build`) |
| **Область доступу (scope)** | Тільки `app/data/catalog.json`, і то опосередковано — через `loadCatalog()` з `app/dist`. Сервер не приймає шляхів ззовні, тож із нього не можна прочитати довільний файл |
| **Секрети** | Немає |
| **Версія** | Власний код у цьому ж репо |

**Які tools він дав агенту** (виміряно через `tools/list`): `search_inventory`,
`check_stock`, `low_stock` + resource `inventory://catalog`.

**Перевірка, що працює:** повний JSON-RPC handshake по stdio, потім реальні
виклики. `low_stock` повернув усі 9 SKU, `resources/read inventory://catalog`
повернув `inventoryValue: 46152` — обидва збігаються з ground truth,
порахованим незалежно. Сирі відповіді — у [`../ab-validation.md`](../ab-validation.md).

## Що НЕ підключали і чому

- **fetch** — розглядав і свідомо **відмовився**. Це єдиний із рекомендованих
  серверів, який тягне контент із довільних URL, тобто заводить у контекст
  агента текст, який пише хтось інший. Для завдання, де вся цінність — 24
  локальні товари, це чистий приріст поверхні атаки без жодної користі.
  (Додатково: пакет ставиться через `uvx`, а не npm — див. «Дефекти» нижче.)
- **git** — користі мало (я і так працюю в git через звичайні команди), а
  сервер отримав би доступ до всієї історії репо, включно з тим, що могло бути
  закомічено й видалено. Не вартує того.
- **everything** (`@modelcontextprotocol/server-everything`) — демо-сервер із
  навмисне широким набором можливостей. Годиться, щоб побачити протокол, але
  не для конфігу, який комітиться командою.

## Область доступу — головне

Найвужчий scope тут — у **власного сервера**: він не приймає шляхів взагалі,
тому не існує аргументу, яким його можна змусити прочитати щось поза
каталогом. filesystem-сервер, навпаки, приймає шлях — і саме тому його
аргумент звужено до `app/data`, а не до кореня репо. Різниця між «приймає шлях
і обмежений» та «шляхів не приймає в принципі» — це різниця між обмеженням і
неможливістю, і друге завжди сильніше.

## Дефекти стартового репо, знайдені на цьому кроці

1. **`.vscode/mcp.json` неможливо закомітити.** Walkthrough (крок A.2) і
   `.coderabbit.yaml` (`path_filters`) обидва пропонують `.vscode/mcp.json` як
   місце конфігу, але кореневий `.gitignore` містить `.vscode/*` із єдиним
   винятком `!.vscode/extensions.json`. Учасник на VS Code створить конфіг,
   `git add -A` мовчки його проігнорує, і перевірка Task A впаде без
   зрозумілої причини. Потрібен ще один виняток: `!.vscode/mcp.json`.
2. **`git` і `fetch` не ставляться з npm.** Walkthrough рекомендує їх поряд із
   filesystem/memory, ніби вони однорідні, але `@modelcontextprotocol/server-git`
   і `-server-fetch` у npm **не опубліковані** (перевірено `npm view`) — це
   Python-пакети під `uvx`. На машині без Python/uv (як ця) вони недоступні.
   Варто позначити це в walkthrough.
