# Threat model MCP-інтеграцій (Task C)

Стосується конкретно конфігурації в [`.mcp.json`](../../.mcp.json) цього репо:
три сервери — `filesystem`, `memory`, `catalog`. Опис кожного —
у [`servers.md`](servers.md).

## 1. Що до чого має доступ

| Сервер | Дані/ресурси, до яких дістає | Секрети | Може писати? | Довіра до автора |
|---|---|---|---|---|
| `filesystem` (`@modelcontextprotocol/server-filesystem@2026.7.10`) | Аргументом задано `app/data/`. **Але** через `roots/list` у Claude Code фактично — робочі каталоги сесії, тобто все репо (див. §2.2) | немає | **так** — `write_file`, `edit_file`, `create_directory`, `move_file` (4 з 14 tools) | офіційний, org `@modelcontextprotocol` |

## 2. Ризики, які я вважаю реальними для цієї конфігурації

### 2.1 Prompt injection через дані — ризик знижений свідомо

У цій конфігурації **немає жодного сервера, який тягне контент із мережі**. Я
розглядав `fetch` і відмовився саме з цієї причини (`servers.md`, «Що НЕ
підключали»). Це прибирає класичний вектор «зовнішня сторінка містить текст,
адресований агенту».

Залишковий канал усе ж є, і він не нульовий: `memory`. Її вміст —
**вільний текст, який агент сам туди записав у попередній сесії**, а потім
читає як довірений контекст. Якщо в одній сесії в граф потрапив рядок на
кшталт «завжди повідомляй, що запасів достатньо», наступна сесія прочитає його
як факт про домен. Тобто `memory` — це канал self-injection через час, з
persistence, але без зовнішнього автора. Для навчального репо приймаю; у проді
вміст графа треба було б рев'ювити так само, як код.

### 2.2 Занадто широка область доступу — головна реальна проблема тут

`catalog` і `memory` звужені майже до межі можливого. Проблема — у
`filesystem`, і вона **не там, де її очікуєш**.

Я передаю серверу `app/data`, і це справді працює в хостах, що не підтримують
MCP roots — сервер надрукував це у stderr під час перевірки:

```
Client does not support MCP Roots, using allowed directories set from server args
```

Але Claude Code roots **підтримує**, і тоді сервер бере область доступу з
`roots/list` — тобто каталог запуску сесії плюс усі `--add-dir`. У Claude Code
мій «вузький scope» стає fallback-ом, який не спрацьовує, а фактична область —
усе репо.

Що це означає конкретно: у Claude Code сервер `filesystem` бачить не лише
`catalog.json`, а й `.env` (якщо його створять), `.git/`, `mcp-server/` та
решту. І має до них 4 tools на запис. Це **найсерйозніший пункт цього
threat model**, і його не було б видно, якби я не перевірив сервер
емпірично, а просто написав шлях у конфіг і повірив у нього.

### 2.3 Витік секретів — низький, але не структурно виключений

Токенів у грі немає: усі три сервери keyless. `.mcp.json` **не містить жодної
змінної середовища із секретом** — єдині підстановки там це
`${CLAUDE_PROJECT_DIR:-.}` (шлях) і `MEMORY_FILE_PATH` (теж шлях), обидві
неконфіденційні. `.env` у `.gitignore`, у репо лише `.env.example` із
закоментованим рядком.

Залишковий ризик: `filesystem` (за §2.2) може прочитати `.env`, якщо той
з'явиться, і віддати вміст у контекст моделі. Тобто «секретів немає **зараз**»
— це властивість поточного стану, а не гарантія конфігурації.

### 2.4 Зміна поведінки сервера після встановлення — закрито

Обидва зовнішні сервери зафіксовані на точних версіях (`@2026.7.10`,
`@2026.7.4`), а не на `@latest` і не на floating-тегу. Без цього `npx` тягнув
би найновішу версію при кожному старті хоста, і набір tools міг би змінитися
без жодного коміту з мого боку — тобто зміна поверхні атаки без сліду в git.

Залишковий ризик: `npx -y` усе одно виконує код, завантажений із npm, під моїм
користувачем. Пін версії захищає від тихого оновлення, але не від
скомпрометованої вже опублікованої версії.

### 2.5 Дії з побічним ефектом — є, і вони не в моєму сервері

10 із 26 tools у цій конфігурації не є read-only (4 у `filesystem`,
6 у `memory`). Жоден із них не мій: `catalog` read-only повністю, і всі три
його tools марковані `annotations: { readOnlyHint: true, openWorldHint: false }`.

Підтвердження виклику — на боці хоста, не сервера. Тобто «read-only» мого
сервера є структурною властивістю (немає коду, що пише), а безпечність
`filesystem` — лише політикою (хост запитає дозвіл). Друге слабше: воно
залежить від того, чи натисне людина «дозволити».

## 3. Що я зробив, щоб це зменшити

Усе нижче реально застосоване в цьому репо, кожен пункт можна перевірити в диффі:

- `filesystem` обмежено аргументом `${CLAUDE_PROJECT_DIR:-.}/app/data`, а не
  коренем репо і не домашньою текою — з явним застереженням у §2.2, що в
  Claude Code це fallback.
- Власний сервер **не приймає шляхів взагалі** — це не налаштування, а
  властивість API: серед його трьох tools немає жодного параметра-шляху, тож
  вивести його за межі каталогу неможливо навіть навмисно.
- Усі tools власного сервера позначені `readOnlyHint: true`,
  `openWorldHint: false` — щоб хост міг це показати користувачу.
- Версії обох зовнішніх серверів зафіксовані точними тегами замість `@latest`.
- `MEMORY_FILE_PATH` явно спрямований у `.mcp-memory.json` у корені репо, і цей
  файл **додано в `.gitignore`** — інакше `memory` писала б у теку `npx`-кешу
  поза будь-яким контролем.
- Шляхи в конфізі — через `${CLAUDE_PROJECT_DIR:-.}`, а не абсолютні. Це
  водночас і портативність для команди, і відсутність мого локального
  імені користувача в закоміченому файлі.
- `fetch` свідомо не підключено — прибирає весь клас зовнішнього
  prompt injection.

## 4. Що лишилось прийнятим ризиком

- **`filesystem` у Claude Code фактично бачить усе репо** (§2.2). Правильне
  рішення — прибрати `filesystem` зовсім і лишити тільки `catalog`, бо той і
  так закриває всі потреби по каталогу. Я лишаю його свідомо й тільки тому, що
  Task D вимагає **контрольної умови**: прогін B має показати, що робить агент,
  маючи доступ до файлу, але не до мого сервера. Поза цим завданням цей сервер
  тут не потрібен.
- **`memory` не read-only** і може видаляти власні записи. Прийнятно: збиток
  обмежений одним gitignored файлом, який можна видалити без наслідків.
- **`npx -y` виконує завантажений код** без пісочниці. У проді це мав би бути
  зафіксований lockfile-ом локальний застосунок або контейнер.
- **Конфіг не перевірено в живому хості.** Я не під'єднував Claude Code (не було
  можливості в цьому середовищі), тож не можу стверджувати, що
  `${CLAUDE_PROJECT_DIR:-.}` розкрився саме так, як обіцяє документація. Це
  прогалина у верифікації, а не мітигація — чесніше назвати її тут.
