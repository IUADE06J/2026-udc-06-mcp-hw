**Тема:** MCP (Model Context Protocol)
**Формат:** artifacts-first — ви підключаєте чужі MCP-сервери, пишете власний,
описуєте модель загроз і A/B-тестом перевіряєте, чи він узагалі щось змінив

## 0. Налаштування

```bash
gh repo fork koldovsky/2026-udc-06-mcp-hw --clone
cd 2026-udc-06-mcp-hw
git checkout -b ws06/<github-username>

cd app && npm install && npm test && npm run build && cd ..
```

`npm test` — 8 зелених тестів. `npm run build` створює `app/dist/`, з якого
ваш сервер імпортуватиме доменні функції. **Зробіть build до Task B**, інакше
сервер не запуститься.

Потрібно: MCP-сумісний хост (Claude Code, Cursor, VS Code або інший), Node 22+,
GitHub account. API-ключі **не потрібні** — усе завдання проходиться на
безкоштовних серверах без токенів.

> **Спершу прочитайте [`materials/domain-brief.md`](../materials/domain-brief.md)** —
> там описано, що саме має виставляти ваш сервер і чому логіку треба
> **імпортувати з `app/`, а не переписувати** всередині сервера.

## Task A — підключити 2+ публічні сервери _(~25 хв)_

**Мета:** відчути, що підключення сервера — це не «додати рядок у конфіг», а
рішення про те, скільки доступу ви віддаєте.

1. Оберіть **щонайменше два** публічні сервери. Жоден із рекомендованих не
   потребує токена, але зверніть увагу на середовище виконання:

   | Сервер | Запуск | Що треба мати |
   |---|---|---|
   | **filesystem** | `npx` | лише Node — найпростіший старт |
   | **memory** | `npx` | лише Node |
   | **git** | `uvx` | Python + [`uv`](https://docs.astral.sh/uv/) |
   | **fetch** | `uvx` | Python + `uv` |

   Якщо `uv` немає — беріть два npx-сервери (filesystem + memory) і не витрачайте
   час; ставити Python заради домашки не треба. Можна й інші сервери — тоді
   поясніть вибір у документі.
2. Зареєструйте їх у конфізі свого хоста — `.mcp.json` у корені репо
   (Claude Code), `.cursor/mcp.json` (Cursor) або еквівалент. **Закомітьте
   цей файл** — це конфіг рівня проєкту, він призначений для команди.
3. **Звузьте область доступу.** Для filesystem-сервера вкажіть шлях до цього
   репозиторію (або навіть до `app/data`), а не домашню теку і не `/`. Це
   найважливіший рядок усього завдання.

   > 🔎 **Нюанс, який варто побачити на власні очі.** Аргумент зі шляхом — це
   > *запасний* варіант. Якщо хост підтримує `roots`, сервер бере область
   > доступу з нього, а не з вашого аргументу; у stderr filesystem-сервера тоді
   > видно рядок на кшталт `Client does not support MCP Roots, using allowed
   > directories set from server args` — саме коли підтримки НЕМАЄ. Тобто
   > реальний скоуп може визначати хост. І пам'ятайте: `roots` за специфікацією
   > — механізм координації, а не безпеки (сервер *SHOULD* їх поважати, не
   > *MUST*), та ще й позначений deprecated у ревізії `2026-07-28`. Справжня
   > межа — права ОС, окремий користувач або пісочниця. Загляньте в stderr
   > свого сервера й зафіксуйте у `servers.md`, що ви побачили насправді.
4. Якщо якийсь сервер потребує токена — **тільки** через `${ENV_VAR}` у конфізі,
   значення в `.env` (гітігнориться). Літерального ключа в репо бути не може.
5. Заповніть `docs/mcp/servers.md` за шаблоном `docs/templates/servers.md`.
6. Додайте в `app/AGENTS.md` секцію `## MCPs` — перелік підключених серверів і
   навіщо кожен.
7. **Перевірте**, що сервери справді підключились: подивіться список tools у
   хості й попросіть агента зробити щось, що потребує саме цього сервера.

**Перевірка:** конфіг закомічено, ≥2 сервери, жодного літерального секрета,
scope вузький і пояснений, `## MCPs` є в `app/AGENTS.md`.

> Порада: у `servers.md` є рядок «Що НЕ підключали і чому». Свідома відмова від
> сервера з надто широкими правами — теж інженерне рішення, і воно цінується.

## Task B — власний MCP-сервер _(~40 хв)_

**Мета:** зрозуміти MCP зсередини — сервер це звичайний процес, який говорить
узгодженим протоколом.

1. Створіть `mcp-server/` — скопіюйте скелет із коментарями:
   `cp -r docs/templates/mcp-server ./mcp-server && cd mcp-server && npm install`.

   > ⚠️ **Офіційний TS SDK існує у двох поколіннях**, і це найчастіша причина,
   > чому знайдений у статті приклад не збирається: **v2** — пакет
   > `@modelcontextprotocol/server`, **v1** — пакет `@modelcontextprotocol/sdk`
   > з імпортами на кшталт `@modelcontextprotocol/sdk/server/mcp.js`. Шаблон
   > написаний під v2; v1 теж приймається — просто зазначте це в PR. Точні
   > сигнатури звіряйте з документацією **своєї встановленої версії**
   > ([ts.sdk.modelcontextprotocol.io](https://ts.sdk.modelcontextprotocol.io/)),
   > а не зі статті в блозі.
2. Реалізуйте **щонайменше 2 tools** і **щонайменше 1 resource** над каталогом.
   Природний мапінг (не обов'язковий) — у `materials/domain-brief.md`.
3. **Імпортуйте доменні функції з `app/`** (`app/dist/index.js` після build) —
   не переписуйте логіку каталогу в сервері. Сервер має бути тонким адаптером.
4. Тримайте сервер **read-only**: жодних tools, які пишуть файли, видаляють
   дані чи ходять у мережу. Це і вимога завдання, і головна ідея least
   privilege.
5. Кожен tool має **опис і схему вхідних параметрів**. Опис — це те, за чим
   модель вирішує, чи викликати tool; розмитий опис = tool не викликається.
6. Зареєструйте свій сервер у тому ж конфізі, що й у Task A, і **переконайтесь,
   що хост його бачить**: tools мають з'явитися у списку.

**Перевірка:** сервер запускається, ≥2 tools + ≥1 resource видно в хості,
логіка імпортована з `app/`, немає жодного tool із побічним ефектом.

> Найчастіша помилка на цьому кроці — сервер «працює», але хост його не бачить.
> Майже завжди причина в шляхах: хост запускає сервер не з вашого терміналу,
> тож усі шляхи мають бути абсолютними або обчисленими від файлу сервера.
>
> ⚠️ Окремо підступне: TypeScript **не переписує** відносні імпорти при
> компіляції. Якщо `server.ts` лежить у корені пакета, а збірка йде в `dist/`,
> то `../app/dist/index.js` у зібраному файлі вже означає інший каталог — і
> `tsc` про це промовчить. Тому в шаблоні код лежить у `src/`: `src/` і `dist/`
> на однаковій глибині, тож один і той самий шлях коректний в обох.

> 💡 **Перевірити сервер можна й без хоста** — це найшвидший спосіб відділити
> «мій сервер зламаний» від «модель не захотіла викликати мій tool»:
>
> ```bash
> npx @modelcontextprotocol/inspector --cli node ./dist/server.js --method tools/list
> ```
>
> Або напряму по stdio, без Inspector:
>
> ```bash
> printf '%s\n' \
>   '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{},"clientInfo":{"name":"t","version":"1"}}}' \
>   '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
>   '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' | node ./dist/server.js
> ```

## Task C — модель загроз _(~20 хв)_

**Мета:** побачити, що ви щойно розширили поверхню атаки, і свідомо це оцінити.

1. Заповніть `docs/mcp/SECURITY.md` за шаблоном `docs/templates/SECURITY.md`.
2. Таблиця «хто до чого має доступ» має містити **ваші реальні сервери**, а не
   абстрактні приклади.
3. Ризики прив'яжіть до своєї конфігурації: якщо у вас є сервер, що тягне
   контент ззовні — опишіть, що станеться, коли в тому контенті буде текст,
   адресований агенту.
4. Перелічіть мітигації, які ви **реально застосували** в цьому репо, а не
   загальні поради.
5. Чесно вкажіть, що лишилось прийнятим ризиком.

**Перевірка:** документ описує саме вашу конфігурацію — його не можна було б
скопіювати в чужий проєкт без змін.

## Task D — A/B-валідація _(~25 хв)_

**Мета:** перевірити, чи ваш сервер узагалі щось змінив — і бути готовим до
того, що відповідь буде «майже нічого».

1. Візьміть промпт дослівно з `materials/ab-question.md`. **Не змінюйте його
   між прогонами.**
2. Порахуйте ground truth локально (команда — там же), щоб було з чим звіряти.
3. **Прогін A:** сервер підключено, новий чат → запишіть, які tools викликав
   агент і чи правильна відповідь.
4. **Прогін B:** приберіть сервер із конфігу і **перезапустіть хост** (стара
   сесія може ще тримати tools), новий чат, той самий промпт → запишіть, що
   агент зробив натомість.
5. Заповніть `docs/ab-validation.md` за шаблоном.

**Перевірка:** обидва прогони описані конкретно, є таблиця відмінностей і
висновок, немає плейсхолдерів `<...>`.

> ⚠️ **Чесний нульовий результат тут — повноцінний результат.** Цілком
> імовірно, що агент і без вашого сервера прочитає `catalog.json` і порахує
> правильно. Якщо так сталося — так і напишіть, і поясніть, що це означає:
> коли власний MCP-сервер вартий своєї ціни, а коли достатньо файлового
> доступу. Вигадана різниця цінується значно нижче за чесний нуль із
> поясненням.

## Task E (bonus) — оберіть один шлях _(~15 хв)_

Заповніть **один** розділ у `docs/task-e-bonus.md` (шаблон —
`docs/templates/task-e-bonus.md`):

- **Шлях 1 — крос-хост:** той самий сервер у другому хості. Що довелось
  змінити — сам сервер чи лише конфіг?
- **Шлях 2 — MCP Inspector:** продебажте свій сервер Інспектором. Що побачили,
  що завдяки цьому полагодили?
- **Шлях 3 — сервер із токеном:** підключіть сервер, якому потрібен ключ,
  безпечно: мінімальні права, `${ENV_VAR}`, доказ що секрет не в репо.

**Перевірка:** один шлях заповнений повністю. Необов'язкове; відсутність — не
помилка.
